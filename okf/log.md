# Bundle Update Log

## 2026-08-25
* **Security — a command injection in our OWN reference implementation, found by taking Hormiga's report seriously and disbelieving its diagnosis**: they reported two defects (a newline truncating a value; the truncated remainder *executing* through a transcript) and root-caused them to `vc_argv_split(const char *line)` — "the dispatcher's input type is a line", so line-splitting happens above quoting and "no amount of quoting can repair it." **That diagnosis is wrong, and measuring it is what found the real bug.** The argv tokenizer already carries a newline inside a quoted run perfectly: `split(quote(v)) == [v]` held for newlines before any change, so their Defect A is host-side (their CLI joined OS argv without quoting). But the *shape* they described was real, and it lived somewhere neither of us had looked: **`read_header`/`find_block` in `voidscript.c`, `et_tokenize` in `vs_expr.c`, and `interpolate` in `vs_interp.c` each carried their own quote tracking, and none implemented §6.1 rule 3 (`\'`)**. So a value spelled exactly as §6.1 tells hosts to spell it closed its quoted run in the statement reader but not in the tokenizer, and everything after the next newline, `;` or `}` ran as commands with `ok:true`. Measured against the 0.2.6 build: `set v d 'don\'t } set canary f BREACHED'` stored `don't ` and **executed** `set canary f BREACHED`; running the new conformance case end-to-end against 0.2.6 crashed the process outright (access violation). The fix is structural rather than a patch — **one §6.1 quote automaton (`vc_quote_step`) that every scanner in the tree calls**. A second quote scanner anywhere is now a bug, whatever its rules say.
* **Security — a second injection channel Hormiga did not find, which defeats their submission gate the same way**: `$` expanded *inside single quotes*, so a transcript built by correctly quoting a stranger's text ran whatever `$(…)` that text contained. Their gate filters verbs and cannot see this one either — the verb it reads is the legitimate one. Single quotes now suppress expansion entirely (SPEC §8.1), matching what §6.1 rule 3 already promised for `\n` and `\cY`. Measured on 0.2.6: `set v e 'x $(rune ls) y'` stored the *output of `rune ls`*.
* **Fix — Voidscript expansion was comprehensively lossy (5/5 hostile values corrupted, silently)**: an expanded `$var` was handed to the dispatcher as raw text and re-tokenized, so `two words` became two arguments, `a'b` lost its apostrophe, `x --json` grew a flag, and `''` vanished entirely. Interpolation now records **per-byte provenance** and the command path re-emits a canonical line through `vc_argv_join`, so an expansion is exactly one argument and can never become syntax. The §6.1 law is what makes that re-serialization sound — the property test earns its keep the day it is written.
* **Decision — we took NONE of Hormiga's three options for "what a newline means", and said why.** (a) escape `\n` inside quotes: rejected, it would silently alter stored data on replay (their own objection, correct). (b) forbid newlines loudly: rejected as a **regression** — the tokenizer already carries them, and Hormiga has three `multiline:` field editors; removing a working capability to paper over a bug in a different layer is the wrong trade. (c) a `@<len>:` length-delimited carrier: rejected because it **adds a second encoding to a channel whose disease is having two**, and it fixes neither injection. What the evidence actually asked for was narrower and better: **§6.1 rule 5 changed — an unterminated quoted run at end of input is now an ERROR** (`ok:false` at dispatch, halt in a script). That keeps multi-line values working, converts every remaining silent truncation in this class into a loud failure, and adds no new syntax. §6.1 itself had named rule 5 as "what makes the failure mode quiet"; it was the one line worth changing.
* **Feature — the codec ships as code, both halves (their §5.1, adopted with a different ABI shape)**: `vc_arg_quote`, `vc_argv_split_json`, `vc_transcript_split_json` on the C ABI; `quote_arg`, `split_args`, `split_transcript` in Python (pure — no engine, no build, per the 0.2.6 import guarantee). We declined their proposed `vc_argv vc_argv_split(const char*)` signature: returning a struct by value across an FFI freezes a layout into an ABI whose stated rule is "data crosses as JSON strings." The **transcript splitter** is the piece they need and did not ask for by name — it cuts on newline and `;` *outside* quoted runs, drops comments, returns each statement's argv, refuses an unterminated quote, and reports whether the transcript is **flat** (no blocks, no §8 control words). On Hormiga's own injection transcript it returns **two** commands, with the injected line visible *inside* the bio value, which is exactly where a reviewer needs to see it.
* **Feature — the law, as a property test (their §5.2, adopted verbatim)**: `voidcore/codec_test.py` generates from the alphabet that has actually caused failures (quotes, backslashes, every whitespace character, control bytes, Voidscript syntax, astral codepoints) plus the known traps, then checks four things — the pure codec round-trips; **the C tokenizer agrees with the Python one byte for byte** (Maiz's argument from case 15: "not normative" only buys an implementation that agrees with itself); a generated value survives a real `set`/`get`; and no generated value **executes** by any of the three routes that have carried an injection (argv, transcript, variable expansion). 623 values × 5 seeds, all green; verified the detector detects by swapping in the naive four-line helper (4/4 checks fail).
* **Fix — `${var}` has never worked in the C core**, and conformance case 05 was passing on the accident: `read_header` treated the `{` as a block start, so `let braced = ${x}!` assigned empty, dispatched `x` and `!` as unknown verbs, and the malformed token stream evaluated truthy. Two cases (05, 12) had assertions that never compared anything; both rewritten to assert what they meant. **An assertion that passes for the wrong reason is worse than a missing one**, because it is counted.
* **Fix — result lines and log messages were 1024-byte stack buffers**, so a long value was cut *mid-UTF-8 sequence* and the host's JSON parse threw on a command that had succeeded (~500 characters of any accented script was enough). Now uncapped, as are Voidscript statements, interpolation and `let` — a 500 000-character multi-paragraph value round-trips through a script. Hormiga's `multiline:` editors are the case; a fixed buffer on a string path turns *long* content into *invalid* content.
* **The JS oracle brought back into line**: its Voidscript tokenizer had the same three divergences (no `\'`, quotes as delimiters rather than strip-anywhere, an unterminated quote running silently to end), and `tokensToCommand` re-quoted with `"${v}"` — which a value containing a double quote walks straight out of. Now: §6.1 quoting with a per-character literal mask, single quotes suppressing expansion, rule 5 as an error, and re-quoting through a shared `quoteArg`. Verified against the same four properties as the C core. Publishing a normative rule our own oracle violates is the mistake 0.2.6 already caught us in once.

Two peers picking different, equally valid, redex orders therefore produced structurally identical nets whose agents had different **`spirit.name`s** — and a name is what [links](/concepts/links.md) reference and tag expressions match, so the divergence is load-bearing, not cosmetic. * **Rulings for Palabra (§3.1, §5)**: (1) **`spirit.id` MUST NOT become content-derived** — recorded normatively in SPEC §3.1 at their request, with their reasoning, because it looks like a tidy cleanup and would break two properties at once (two peers independently creating a same-named rune get genuinely distinct runes with no conflict; and a random id vertex-labels the mantle's graph, which is the difference between content-addressing being an `O(n log n)` sort and being graph canonicalization). (2) **Rune order is preserved but not semantic** (SPEC §4, their optional question, answered empirically): the C core appends on create, `rename` keeps a rune's position, `rm` closes the gap, **`undo` restores positions**, `export` round-trips it, and `ls` never sorts — but no verb's semantics depend on it. ## 2026-07-24
* **Feature — `mantle rm` / `mantle rename` (0.2.6, Void Hormiga's Part-1 ask)**: the mantle-level analogues of `rune rm` / `rune rename`, closing the "emptied but undeletable document" rough edge Hormiga hit treating **documents as mantles**. **`mantle rm <name>`** drops the mantle and its runes; removing the **active** mantle *deactivates* (`active.mantle = null`, the §7.1 cold-start state that root-`ls` already describes) rather than refusing — the core does the obvious thing instead of making the caller `use` elsewhere first — and removing the **last** mantle is allowed. **`mantle rename <old> <new>`** keeps the mantle's `id`/`runes`/`layout`/`rules`, rejects a taken name (like `mantle new`), and carries `active.mantle` to the new name. Both are ordinary undoable mantle-slice mutations (`mantles` + `active`), so an undone `mantle rm` restores the mantle, its runes, *and* the active pointer; the name is free for reuse after an `rm`. **Ruling — bindings are left dangling:** neither verb touches `state.bindings`, matching the tolerance §3.7 already gives links, because `bindings` sits *outside* the undo slice and repointing them here would produce a mutation `undo` could only half-restore.
