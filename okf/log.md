## 2026-09-02
* **Feature — a correct answer that read as a false one: `related` now names the verb that can see the edge (`core/src/dispatch/verbs_graph.c`, SPEC §7.2)**: Void Hormiga filed this as *"not a defect"* and they were right, which is what makes it worth acting on. A field agent wrote `link click-dns click-pages --relation 3:1`, asked `related click-dns`, got **`(no neighbors)`**, found the edge sitting in `layout/edges`, and concluded `link` was broken. Nothing was: `related` reads `mantle.tags[<tag>].near`, which only `relate` writes, and `links` reported the edge correctly. But **a rune's name doubles as a tag**, so `related <rune>` is accepted and answers confidently, and an empty answer is indistinguishable from *"this thing has nothing attached to it"* — so the agent may reasonably have written the link twice. We declined the reading that would collapse the two verbs (they model different graphs and merging them would be worse than the confusion) and took their one-line suggestion exactly: when the ref names a rune **that has edges**, the empty answer says so — `(no tag neighbors; 'click-dns' is a rune with 1 link - try ``links click-dns``)`. One lookup, only on the path where the answer is already empty, and it never fires for a plain tag or an edgeless rune. **The difference between a dead end and a signpost.**
* **Fix — `relate` wrote the *opposite* of what was asked, and reported ok**: Hormiga's second item was *"`relate` accepts `--relation <name>` and ignores it"*. It was worse than ignoring. The weight is positional (`relate <tagA> <tagB> [weight]`), so `relate a b --relation friend` reached `atof("--relation")`, which is **0.0**, and wrote the association at weight **zero** — "not near at all", the inverse of the intent — while returning ok. `relate` takes no flags; a weight that is not a number is now an error naming the offending token. The same rule catches a plain typo (`relate a b abc`), which had the identical silent-zero outcome. Strict parse via a local `vc_parse_number`, matching the coordinate check `place` already uses — `atof` answers 0.0 for a flag, a typo and a real zero alike, which is why nothing in the tree should call it on user input.
* **Fix — the `help`/`--describe` verb list had four holes, not one**: Hormiga found `link` missing from the flat `verbs` string, and noted the honest reason — *"the rest of that briefing is introspected from live registries and is trustworthy; that one list is hand-maintained."* Diffing it against the router turned up **`links`, `unlink` and `journal`** missing too, so an agent reading the briefing would conclude four verbs did not exist. All four added. There is nothing to introspect (the router is an `if`/`else` chain across five family files), so the list is now **checked** instead: `bindings/python/describe_verbs_test.py` extracts every `!strcmp(v, "…")` the families answer to and diffs both directions — missing verbs *and* phantoms the list promises. 48 dispatched verbs, all listed, no phantoms; detector verified by planting a verb nobody listed. The next omission fails a test rather than costing an agent an hour.

## 2026-08-31
* **Feature — `patch`, the content rule: a game's content stops being code (`conformance/reduce/README.md` §2)**: 0.2.11 shipped composition and said plainly that the data rule set could not express a content change, so *"the equipped dye makes the shirt purple"* stayed a code-registered `expand`. Void Unity answered with a measurement rather than an opinion, and it is the whole argument: **the player is a mantle and one rune in the world → data; the amulet meets the shirt and nothing reaches the voice → data; the shirt comes out purple → C#, behind a recompile.** *"A game's rule set is mostly content changes with a little structure, and today the structure is data and the content is code."* The third row is the one a designer changes on a Tuesday afternoon and it was the one behind a build. `patch` is the third data rule — `{"glyphs": ["dye","cloth"], "rule": "patch", "keep": "cloth", "copy": {"colour": "colour"}, "set": {"dyed": true}}` — one pair, one survivor named by `keep`, `copy` reading fields off the **consumed** agent, `set` writing literals last so they win, a missing source field **skipped** rather than written as null. **Case 25 is the entire worked scenario as data with no code at all.**
* **Three properties are the whole of `patch`'s contract, and each is load-bearing.** (a) **Content-only** — same id, glyph, arity, tags and aux wiring; only content differs. (b) **It creates no active pair**: the survivor's principal is freed and nothing rewires to it, so `patch` cannot make a terminating rule set non-terminating and a second dye cannot queue on the same garment — pinned by a fixed-point test rather than asserted. (c) **Distinct glyphs required**, refused at *spec-compile* time: on an unordered same-glyph pair "which side survives" has no answer that is not an arbitrary tiebreak, and an arbitrary tiebreak on an unordered pair is exactly the schedule-dependence the derived-id rule exists to remove. Deliberately weaker than an arbitrary rewrite — close to the shape Unity said they reach for — so the one-rule-per-unordered-pair confluence guard still buys what it buys. A rule that must *restructure* on contact is still a code-registered `expand`, and that is now the honest edge of the data form.
* **`patch` keeps the survivor's id, and that is where the two asks meet.** A deliberate exception to §2's derived-id rule, which governs an agent a rule *creates* — and `patch` creates none, it hands one back. Honest reading (same glyph, same arity, same wiring, same tags: it is the same shirt), still schedule-independent (an **input** id), and it means a boxed agent keeps its `<rune>/` provenance through a content rewrite. Case 25's pinned ids are `["cord", "p1/shirt", "p1/skin", "p1/voice"]` — the shirt was dyed and is still `p1`'s shirt.
* **Feature — a rule-created agent inherits its parents' box (§2)**: Unity's second ask, and the useful thing they did was **separate it from the one we had assumed it was**. They do not want `from_net` to re-box a normal form — they agreed with our reasoning that after a rewrite spanning a boundary there is often no fact of the matter, and asked us **not** to build it. What they want is narrower and nearly free: *"the minter key already contains the two parent ids."* A derived agent is now prefixed with the **longest common box path** of its parents (`p1/silk` × `p1/wand` → `p1/_r<hex>`; `guy/h/finger` × `guy/torso` → `guy/`), because a host's job with a normal form is to **draw** it, which means answering *"which entity is this agent"* for every agent — and a derived one had no answer, only the accident of being wired to something that still carried a prefix. Decidable rather than heuristic; the rewriter is already holding both ids. Cases 23 and 24.
* **The ambiguous case stays ambiguous, on their preference and ours.** Parents from two different boxes share no path and get **no** prefix, because such an agent genuinely has no owner. Their words, quoting our own ruling back: *"a message implying a resolution that does not exist is worse than one that says nothing"* — the same choice `validate` makes about an endpoint resolving to a rune in another mantle. Case 24 pins it.
* **Two things that made the prefix safe to ship one release after freezing the digest.** The **digest is untouched** — the prefix names the agent and never enters the key. And in a **flat** net no id contains `/`, so the prefix is always empty and every derived id is byte-for-byte what 0.2.10 produced: cases 15 and 16 did not move, and neither existing implementation of the minter is affected. That property is only true if `/` really cannot appear in a flat agent id, so it is now **reserved**: `to_net` refuses a rune whose name contains one (`adapter-ports`, case 22). A rule that reads structure back out of an id must be a fact rather than a guess, and refusing the input is the standing preference over guessing at it (§6.1 rule 5, same reasoning).
* **Three defects in our own runner, all reported by Void Unity, all found by porting it rather than reading it.** (a) `execute()` recovered a `BoxError`'s abstract kind by **searching its message** for keywords — so rewording a diagnostic silently reclassified a case, which is the one thing a conformance runner must not do. The kind is a field now (`BoxError.kind`), as it was in their port on day one. (b) That sniffing had already produced **one live inconsistency**: a malformed edge naming a non-existent endpoint answered `adapter-ports` through the flat adapter and `box-interface` through the composing one — same defect, same document, two kinds, decided only by whether some *other* rune in the mantle happened to be a box. Both are `adapter-ports`, and **case 21** now locks both paths, because "no shipped case covers it" was the only reason it was not already wrong. (c) A minter vector with `"ordinal": 0` left the result variable unbound and raised a `NameError` instead of saying the ordinal is **1-based**; §5 says so now and the runner checks it.
* **What Unity's report is worth beyond the fixes.** They took §7 to **20/20 on first contact**, test-first, *"close to a transcription"*, and named the three sentences that were doing real work: the interface-is-a-permutation rule (*"we would have written 'declared wins' and drifted"*), namespacing by **rune** rather than by mantle, and a `signatures` entry contradicting a box's arity being an error rather than a tiebreak. Each is one line of spec preventing one class of silent divergence, which is the best evidence yet for writing the *reason* into a contract and not only the rule. They also confirmed `mantles` as a case-level key let all sixteen pre-§7 cases run their runner's identical path with no flag and no branch — and **checked** that rather than assuming it, by comparing a composed net against a flat one.

## 2026-08-30
* **Feature — a mantle can be a rune inside another mantle (`reduce/box.py`, the Reduce seam)**: the thing 0.2.10 predicted and did not build. A **player** is a mantle of body parts and clothing with rules of its own; the same player is one **rune** in the world mantle; and an amulet lying in the world, once equipped, recolours a shirt *inside* the player. Three sentences that look like they need three mechanisms and a compromise between the first two. They need one, and it is a line of theory this project adopted in June: **a net with *n* free ports behaves as an agent of arity *n***. A mantle is a net; a net is an agent; so nothing had to be added to the *model* — only to the **adapter**, which now notices and splices. A **box** is a glyph declared in the reduce spec (`{"boxes": {"player": {"mantle": "player", "interface": [...]}}}`) meaning *a rune of this glyph **is** that mantle*. No C change, no state-document change, nothing blocked behind §12.
* **Encapsulation and reach-in are the same mechanism, and that is the whole result.** Void Unity asked for encapsulation and was explicit that a scope *check* is the wrong shape, because a check is something a future code path can forget. The application asked for the opposite — an outside rune changing an inside rune. Both hold and **neither is enforced by a rule**: the parent can address only the interface, and every other inner port is already wired inside, so **linearity** (every port in at most one wire) means there is no wire between the inner silk and the outer silk *and no way to add one*; while a wire to interface port *k* **is** a wire to a real inner port, so an equipped item meets the garment it is wired to and the effect propagates inward by ordinary reduction. Case 20 pins both halves in one net: the amulet annihilates with the inner shirt, leaving the amulet's chain wired to the player's own skin — an outside agent rewrote the mantle's interior — while `voice` is untouched and *could not* have been, having no port in the interface. Encapsulation as a **property of the net** rather than a check survives every rule set anyone writes later; that is the difference Unity was asking for and it is now structural.
* **The finding that came out of building it, and it changes how a mantle is designed.** An active pair is **principal**-to-principal, so a mantle can only be *interacted with* from outside through **inner principals that are free**. An interface of nothing but auxiliary ports composes fine, wires fine, and never reacts — a net that can be attached to and cannot respond. This is not a limitation to route around; it is the model saying what an interface *means*: "what this mantle exposes for interaction" is exactly "which of its inner principals are free," decided by how the sub-mantle wires **itself**. A shirt is equippable because its principal is unwired — **the socket is the absence of a wire.** Pinned by `test_equip_socket_must_be_a_principal`, which was written after the first draft of the test suite quietly composed a dye onto an aux port and reduced to nothing.
* **An interface orders the boundary and may never redefine it.** The tempting design lets the declaration *select* — expose these ports, hide those — and that makes a box a second source of truth about its own mantle, which then drifts: the mantle grows a rune, its free-port set moves, and the interface goes on describing a boundary that is no longer there. So the free ports **are** the interface, and the list exists for exactly one reason — the parent addresses ports by **index**, and a set has no indices. Omitting a free port, naming a non-free one, or repeating one is `box-interface`; a `signatures` entry contradicting a box's computed arity is an error rather than a tiebreak. Same ruling as 0.2.10's `validate` endpoint kinds and 0.2.5's `placement`-in-content de-sanctioning, for the same reason every time: **do not store a fact about one entity inside another, where nothing keeps it true.** It is also the constraint promised to Void Unity on 2026-08-29 ("must not become a second spelling of the free ports the net already has"), kept.
* **Box or holiday — the boundary taxonomy, because the question was asked and the intuition was nearly right.** [Interaction nets — theory](/design/interaction-nets-theory.md) §2.2 maps *holiday = a free port at a boundary*, so reaching for a holiday when two nets meet is reading the model correctly; it lands one seat over. What decides is **whether you reduce the far side**: another rune in the same mantle → a **wire**; a mantle **you own** → a **box**, and the boundary *dissolves* on composition so you reduce straight through it; a net you **don't** own → a **holiday**, where the port stays free and you exchange along it but never rewrite through it. All three are the same shape — a wire to a port — and differ only in what is at the far end. Player and world are both yours, so that is a box. **A box is composition; a holiday is communication.** Routing an equip through a holiday would put I/O, non-purity and non-previewability in the way of what is pure graph surgery.
* **Instancing falls out, and is normative.** Spliced agent ids are namespaced `<rune>/<agent>` — by the **rune**, not the mantle — so `p1` and `p2` of one player mantle are two independent copies rather than one shared net, which is the difference between a game and a diagram. Nesting composes the prefixes (`guy/h/finger`). Case 17 carries `pin_ids`, so the naming is pinned rather than left to the id-blind canonical form.
* **Stated plainly, three things this does not do.** (a) **No re-boxing on the way out** — `from_net` returns one flat mantle; survivors keep their prefix, but an agent *created by a rule* is named from the redex and carries none, including one created wholly inside a box. Reduction is a whole-net operation and the box is an input structure, not a partition the executor maintains; re-boxing a normal form is an **open question**, not a missing feature, because after a rewrite spanning the boundary there is often no fact of the matter about which side a new agent belongs to. (b) **The data rule set cannot express a content change** — `annihilate` and `commute` are the two data-authored rules and neither writes content, so *"the dye makes the shirt purple"* still needs a code-registered `expand`. The composition half is complete and this half is not, and it is now the thing standing between a game author and writing equipment effects as **data**. (c) `layout.edges` still cannot name a mantle, and nothing here needed it.
* **Docs**: new [mantle composition](/design/mantle-composition.md) (`current`, verified) + design index row; `conformance/reduce/README.md` gains **§7** (composition, the interface rule, why encapsulation and reach-in are one mechanism, the principal-port finding, and §7.2's honest list of what is not done) and the `mantles` case key + three error kinds; [reduce](/concepts/reduce.md) and [links](/concepts/links.md) updated — links records that its `planned` cross-entity work is no longer blocking anyone, since the forcing use case was answered in the adapter; SPEC §7.2's `reduce` row and §12's cross-entity entry record the same, with the 2026-08-29 guess marked as having been right.

Two things worth keeping from their reply. **Case 16 changed their code, not just their diagnosis**: their minter was a lambda inside `apply_rule`, closed over the redex and unreachable from any test, so taking the nine vectors forced `derived_id(...)` public — an isolated-vector case moved a normative rule out of a closure and into a named, callable, testable thing. That is a better argument for that kind of case than the one we made for it. They also confirm the vector we most wanted to be load-bearing: **vector 4** (a flat sort of all four strings) is the one they would have been most likely to fail, and nothing in case 15 distinguishes it. And they declined the apology, with a sharper version of the lesson than ours — *"we argued for normativity and then assumed normative meant bless the incumbent; those are different asks and we only made one of them."* Their §4 is now a one-line **Host gotchas** entry in `core/README.md`: a version floor compared as a **string** breaks at 0.2.10, since `"0.2.10" < "0.2.4"` lexicographically — wrong from the day it is written, unable to fire until a component reaches double digits, theirs rather than ours, and written down once because the hosts behind them will hit it as *"0.2.10 broke my build"*.

## 2026-08-29
* **Ruling — the derived-id digest is normative, and it is SHA-256/48, not our BLAKE2b (`conformance/reduce/README.md` §2)**: Void Unity became the **second implementation** of the Reduce executor (C#, ~900 lines against the reference's ~530) and passed **14 of 15** vendored cases exactly as stored. The fifteenth is the whole message, and their reading of it is right: §2 made derived ids normative *and gave the reason* — merge-by-reduction needs the same **bytes**, not merely the same shape — then declared the digest **not** normative in the next sentence. "Individually reasonable and jointly unsatisfiable." They hold the property (all sixteen of case 15's randomized schedules agree on the literal ids) and still cannot produce our bytes, because they hash with SHA-256 and we hashed with BLAKE2b-48. Two conforming implementations therefore reach normal forms equal only *up to renaming* — the exact situation the requirement exists to prevent — and **nothing raises an error**: Palabra's add-wins join sees different runes and keeps both, so a merge doubles every rule-created agent. Contract working as intended: it caught a real gap on first contact with a second language.
* **Why the digest is SHA-256 and not the BLAKE2b we already had.** Availability, and nothing else — .NET and Unity's Mono have no BLAKE2b, so blessing ours would have forced the second implementer to vendor a cryptographic primitive whose test vectors are **RFC 7693's rather than Void Core's**, inside the one project whose charter forbids reimplementing what has a C ABI unless upstream wrote the vectors that catch it being wrong. Their choosing SHA-256 was that rule being *followed*, not a corner cut. Nothing here is a security boundary: 48 bits is a naming digest and collision resistance is not the property being bought. §2 now pins the whole encoding — `\x1f`-joined, the two glyphs sorted and the two parent ids sorted **separately** (a flat sort of all four is a different key), a 1-based ordinal, UTF-8, `_r` + 12 lowercase hex.
* **The cost is owned, not hidden — and it lands on the host that asked first.** [The effect seam & the session boundary](/design/effect-seam-and-session-boundary.md) §3 had this exact question parked, from **Void Maiz**, with the stance *"agree, this is the cheapest of the four"* — and Maiz had already matched our BLAKE2b **byte for byte** on that encouragement. This change breaks that, so they were told directly rather than left to find it in a red run. It is also the clearest argument yet for parking a one-way door: Maiz asked from C++, where both digests are equally reachable, so the question looked like it had one free answer; Unity asked from a language that has only one of them, and **availability turned out to be the deciding property, invisible from a language that has everything.** Shipping this in August would have blessed BLAKE2b and blocked Unity.
* **New: `16-minter.json`, the minter alone** — key in, id out, no reduction around it (their ask). Case 15 pins the derived-id *property*, which is the right test and the wrong debugger: an implementation whose ids differ there cannot tell a wrong digest from a wrong ordinal from a wrong pair ordering. The nine vectors separate exactly those, including that the two sorted components are not interchangeable. **Reduce conformance 16/16**; only case 15's pinned ids moved, which is the blast radius the id-blind canonical form was designed to give. The runner's `--regen`-against-yourself advice in §6 is withdrawn — it was wrong once the digest is normative, and Unity named a second reason it was always weak: **a host that *vendors* a case directory cannot write to it**, because a vendored copy edited locally stops showing drift, which is the entire reason to vendor one.
* **Fix — `validate` could not tell a tolerated dangle from a real mistake (SPEC §3.7)**: Void Unity's other message, held since their founding. `link player equipment` from inside the `equipment` mantle reported *"dangling edge from 'player'"* and *"dangling edge to 'equipment'"* with equal confidence — but `equipment` **exists**, as a mantle, and only one of those is the tolerance §3.7 grants. Their framing is the load-bearing one: dangling is the case a streaming host is **told to ignore** (a chunk unloads, its links dangle, nothing is wrong), so a diagnostic that also carries real errors is one nobody can safely ignore. `validate` now answers three things per endpoint — resolves to a rune here (fine), names a **mantle** (`cross-kind edge <side> '<name>': names a mantle, not a rune`), names **nothing** (`dangling edge <side> '<name>'`) — and both strings are normative, since branching on them is the point. **Derived on every call, never stored on the edge:** remove the mantle and the same edge reads as a dangle again, which `16-validate-endpoints.vs` pins. Storing the kind would put a fact about one entity inside another, where nothing keeps it true. Also aligned the JS oracle's four `validate` strings to the C core's — they had diverged in **all four**, invisibly, because no case had ever asserted on `validate`'s `data`.
* **Answer — cross-entity links, narrowed and blocked on a named thing rather than on attention (SPEC §3.7, §12)**: Unity's Rung 5 is *mantle as agent* — an equipment mantle appearing in the world mantle as a rune exposing only its free ports — and it is the one host use case blocking on §3.7's planned extension. §3.7 promised rune↔mantle↔holiday; it now promises **rune↔mantle only**, because that is the third anyone is blocked on and a smaller promise is a keepable one. Two things settled ahead of the design: an endpoint stays a **plain name whose kind is resolved** (the same reasoning as above — a `to_kind` flag on the edge would be a stored fact about another entity), and nothing about how links dangle changes. It is **blocked on §12's *scope of the undoable slice***: an edge naming another mantle is the first edge whose meaning lives outside its own mantle, so `mantle rm` and its `undo` need the answer bindings are already waiting on. Told to them as "not soon, and here is what it is behind", which they explicitly asked for over a maybe.
* **And a reframing they can act on today.** The encapsulation Rung 5 actually wants — *the inner `wand × silk` rule cannot reach world silk because there is **no active pair**, not because a filter said no* — is a statement about the **net**, not about the link graph. Links are the passive substrate; they do nothing by construction, so a rune↔mantle *link* would not produce it either. The change that yields it is a **boxing rule in Reduce's mantle adapter** (`to_net`, `conformance/reduce/README.md` §4): a sub-mantle enters as an agent whose ports are the sub-net's free ports. That lives at the **seam**, where Unity already implements the executor, so they can prototype it without a Core primitive and without being the host that invents a second answer to a question the model will answer properly. Recorded in §12 for whoever designs it, with the constraint that a boxed mantle's port declaration must not become a second spelling of the free ports the net already has.
* **Docs**: SPEC §3.7 (endpoint classification + the narrowed extension, normative), §7.2 (the `validate` row; and the **[seam]** marker repeated in **every** transform-verb row — a host reads the verb table before the status paragraph under it, so a tabulated verb answering `unknown verb` reads as a bug until they find the paragraph, which cost Unity a detour), §12 (two new entries: cross-entity links, and a host-verb registration seam so `help` lists what a host added — **two** hosts have now built the superset dispatcher and had their verb be invisible; neither asked, both said they would print their own help); [links](/concepts/links.md) gains the dangle-vs-mistake property and the narrowed `planned`; [the effect seam & the session boundary](/design/effect-seam-and-session-boundary.md) §3 graduates from `planned` to decided, recording that it was decided *against* the digest it was arguing for.

Version **0.2.10**, all five sites agreeing.

That gap predates this work and is not closed by it.

A `\r` was an ordinary character to `read_header`, so a CRLF-authored script **compared wrong values and returned corrupted ones, reporting neither**: `return ok` crossed the C ABI as `"ok\r"`, and `assert a == a` was false with the CR invisible in every terminal that renders the message. What made it expensive is that **numeric** comparison coerces through a trailing CR, so the same script passed or failed depending on which *kind* of value a line happened to compare — an intermittent logic bug, not a newline problem. The root cause is the §6.1 lesson in a smaller costume: `skip_sep` already treated CR as a separator and `read_header` treated it as content. **Two readers, one disagreement.** Fixed by making CR end a statement exactly as LF does, in both statement readers (`voidscript.c`, and `vc_transcript_split_json` in `codec.c`); inside a quoted run a CR is still data. SPEC §8 now states it normatively, because the alternative to "CR is a terminator" is not "LF only" — it is silent value corruption, and §6.1 rule 5 already set the precedent that this project refuses an input rather than truncating a value.
* **Fix — the conformance suite normalized its own inputs, which is why 0.2.7 and 0.2.8 shipped over this (SPEC §11, now normative)**: `conformance/run.py` read each case with `open(path, encoding="utf-8")` — Python **text mode**, whose universal-newline translation rewrites CRLF to LF before the library sees a byte. The suite therefore could not observe the bug **by construction**, and no case could have been written that would. Meanwhile `14-journal.vs` sat in the repository **committed with CRLF** (59 CRLF lines; every sibling LF): green upstream, red for the second implementation that read it faithfully. This is exactly the failure `conformance/README.md` exists to prevent, arriving through the *runner* rather than through a case. The runner now reads bytes and decodes without translation, and SPEC §11 requires that of any runner in any language. New case **`15-crlf.vs`, stored with CRLF on purpose** and marked `-text` in a new `.gitattributes` (which also pins `*.vs` to `eol=lf` so the rest cannot drift again) — verified **red against the pre-fix build and green after**, which is the difference between a test and a decoration. `14-journal.vs` normalized to LF. **15/15 cases pass.**
* **Feature — undo is the host's switch now (`vc_set_undo`, `vc_set_undo_depth`; SPEC §6)**: Void Unity's second message measured what the memento costs when `mantles` holds a **world** instead of a document — one `set` at 4 000 runes took **27.6 ms**, longer than a 60 Hz frame, and building 4 000 runes took **56 s**, quadratic because every `rune new` deep-copies every rune already there. The premise that changed is theirs: *a thing is a rune iff it can be the endpoint of a link*, so the runes are instances — every door, crate, NPC and district in a streaming map. Every previous host kept a document there (Hormiga's topology, Maiz's census, Reyna's archive), and a memento of a document is cheap. **A memento of a world is the world.** They also named the asymmetry precisely: `vc_set_journal`'s own doc comment promises that *"a host that does not ask for the record pays neither the entries nor the id-diff"*, and undo is the same kind of thing — a record kept for a host that might walk it back — with no control at all. Two records, one principle, now one rule. Measured here after the change, at 600 runes: build **498 ms on / 18 ms off**, one `set` **1 808 µs on / 8 µs off**; at 4 000 runes the build goes 29 s → 0.6 s and `set` 15 300 µs → 7 µs. That converts an unusable configuration into a supported one: an **authoring** manager (undo on, journal on, attributed, replayable) and a **world** manager (both off) in one process.
* **Three decisions inside that switch that are not obvious.** (a) **Off means `undo` fails *saying so***, not "nothing to undo" — the host struck that bargain knowingly, but a script running inside it did not, and an empty-stack message would read as a fact about the state. `history` says it too. (b) **Turning undo off drops the frames already held**, unlike `vc_set_journal`, which keeps its entries. That is not an inconsistency: a journal entry is an exported artifact a host can still read after switching off, while an undo frame is only ever consumed by `undo`/`redo` — which now fail — so keeping them would hold exactly the memory the host just declined. (c) **`batch` stays atomic either way**, because its rollback was always its own saved copy rather than the undo stack; a test pins that in both configurations, since it is the property that would break silently if the two mechanisms were ever merged.
* **Stated rather than hidden: this is a switch, not a fix.** The memento is still O(slice) *when it is taken*. The fix is reified commands with inverses — and [command architecture](/design/command-architecture.md) had recorded, one day earlier, that the memory win was "not currently wanted, nothing depends on it." That expired: **two hosts now ask for it**, Void Palabra to describe a change to another machine and Void Unity to avoid describing a change as a copy of a world. Their unrequested third option — a **copy-on-write per-mantle** memento, smaller than reification and needing no new contract, since a command touches one mantle — is recorded on the design page so the choice between the two is made deliberately rather than by whichever is attempted first.
* **Fix — `vc_transcript_split_json` line numbers drifted past a multi-line value (Void Maiz, 2026-08-25)**: `line_no` advanced only in the statement-boundary branch, so a newline consumed *inside* a quoted run was never counted, and every statement after a multi-line value reported a line low by that value's newline count. The same counter feeds `err_line`, so an unterminated quote **later** in such a file was blamed on the wrong line — and "reporting an error with a line number rather than a plausible partial parse" is the entire reason the function exists. Newlines are now counted wherever they are **consumed**, not only where they are honored; `stmt_line` is still taken at the statement's first non-blank byte, so a multi-line statement keeps reporting the line it *started* on. Their deliberately as-is regression test in `VoidMaiz:tests/command_smoke.cpp` will now go red on purpose. Their message also reported the adoption that found it: Void Maiz no longer implements §6.1 anywhere, and deleting their four-line `arg()` — reviewed twice, correct on the day — removed the trailing-backslash bug 0.2.7 had already fixed here.

## 2026-08-27
* **Feature — pure vs effectful, resolved; and commands reified (SPEC §6.2)**: Void Palabra has recorded, since 2026-07-27, exactly **two blockers owned by Void Core** — *reified commands* and *the pure-vs-effectful split* — and they block **all** *utterance* work, which is their non-linear history pillar entire (`VoidPalabra:/concepts/utterance.md`, `/design/open-questions.md` §3.1). Our own [command architecture](/design/command-architecture.md) note had named purity *"probably the single most important distinction to get right"* in July, deferred it, and set one condition on ever reifying: **resolve purity first**. That condition is honored here. The ruling: **a command is effectful iff its verb can reach the host through the effect handler** — `save`, `deploy`, `build`, `preview`, `effect`, and that list is *complete* because `vc_set_effect_handler` is the only way out of a core that does no I/O by definition (§1).
* **The two properties that were not obvious until written down.** (a) **The classification is static, not observed.** `save` is effectful on a host that registered no effect handler, even though nothing left the process. The tempting design — call a command pure when no effect actually fired — makes the *same command* a recordable change on one peer and not on another, which is precisely the divergence the distinction exists to prevent. Observation may **upgrade** a compound command (a `batch` containing a `deploy` is effectful) and never downgrade one, which is how `batch` gets an honest answer without the classification becoming host-dependent. (b) **Effectful commands must still be recorded.** Excluding them from the journal would make `pure` a constant `true` and leave a consumer unable to distinguish *"nothing effectful happened"* from *"a deploy happened and was not recorded"* — and the second silently drops it from a replay.
* **The July design table turned out to pose a false choice.** It read as memento *versus* reified command, one replacing the other, and anticipated a "swap" behind the `is_mutating`/capture/commit seam. What shipped is **both, as two structures**, because their structural requirements are incompatible: the undo stack is **bounded** (drops its oldest frame) and **consumed** (`undo`/`redo` move frames between stacks), while a record that silently forgets, or that *loses* an entry when a change is taken back, is not a record. Undo is untouched and stays memento-based; the journal hangs off the same seam, which was the right seam after all.
* **What `minted` settles, and why it is a diff rather than a hook.** §3.1 ids come from the PRNG, so replaying a command *string* produces different state — which is what makes a bare command log useless as a history, and is the thing Palabra had independently worked out (*"the utterance records the identity that was minted rather than re-deriving it"*). Each entry carries the ids that exist after the command and did not before. It is computed by **diffing the state's id set** across the command rather than by instrumenting `vc_mint_id`, for two reasons: the minting sites live in the model layer, which has no manager to report to, and a recorder reached through a global would break the ABI's promise that **distinct managers are independent across threads** — the one property that makes N dispatchers a real answer to multi-client. The walk skips `content` subtrees, because content is opaque by contract and an app field that happens to be named `id` is none of the core's business.
* **Entry shape and what records**: `{seq, command, verb, who, pure, slice, minted}`. `command` is the **canonical** line (aliases desugared), so `rm x` and `rune rm x` never record as two different changes — the alias rule (§7.1) extended one layer further than it had been. `slice` reports where the change landed (`undo` / `view` / `host`) rather than legislating what belongs where, deliberately leaving §12's undoable-slice question open. Recorded: every **successful** top-level command that is mutating, a view mutation, `undo`/`redo`, or effectful. `undo`/`redo` are in because a record that omits taking a change back replays into a state the author never had. A **failed** command records nothing — it changed nothing, and §9's log is already the record of attempts. `batch` records **once**, matching its one undo frame; nestable commands were not needed to get there.
* **A bug the stress test found, and the rule it produced**: the first working id-diff reported `save` as **minting every id in the document**. `save` copies `mantles` into `_baseline` (§7 dirty-tracking), so the post-image held a second occurrence of every id and the merge-diff read each one as new — an entry claiming a dozen creations that never happened, with `ok:true`. The images now exclude `_baseline` as well as `content`, and both exclusions are **normative** for the same reason stated one level up: *only count identities that are really there, once.* A snapshot is not an identity; opaque content is not the core's business. Verified `revert` still reports what it genuinely restored, which is the case that proves the exclusion did not just silence the symptom.
* **The cost, stated rather than hidden**: filling `minted` is **O(document) per recorded command** — 2000 sequential `rune new` calls took 9.9s unjournaled, 16.4s journaled. Linear per command, quadratic to build a document. The obvious optimization is a table of verbs that can mint, and we **declined it**: an omission from that table under-reports `minted` *silently*, which is the failure class this project keeps paying for. §6.2 permits an implementation to skip the walk only where the proof cannot fail silently.
* **Off by default, and a verb.** `vc_set_journal` / `vc_export_journal` / `vc_journal_clear` on the ABI (additive; the Python binding binds them leniently so it still loads against an older library), plus a **`journal [on|off|clear]` verb** — because the core is agent-drivable *through verbs*, a record an agent cannot read is a record it cannot reason about, and it is what makes the feature testable in the language-neutral suite rather than only in C. A host that does not ask for the record pays neither the entries nor the id-diff. `journal` is itself neither mutating nor effectful, so reading or toggling the record never appears in it. A test asserts that enabling the journal **changes no behaviour** — same `ok` flags, same resulting state document.
* **Answers to the "be careful what it MEANS" analysis owed** (July, five items): railguard **held** (the journal describes; nothing replays it inside the core, so reification did not turn the core into an execution engine); purity **answered**; granularity **answered** (`batch` = one entry); undoable-slice scope **still open**, and not forced; *"are reads commands?"* — **no**, the journal records what changed something, and the RL-trajectory use wants the opposite answer, so if that work lands it needs its own recorder. **Still not done:** commands have no **inverses**, so the O(diff)-per-frame memory win is uncollected and currently unwanted — nothing depends on it.
* **SPEC §12 updated honestly**: the first open question ("undo across holiday-backed data") is now **half**-answered. *Which* commands cross the boundary is normative; what `undo` should *do* about one is not — an effectful command is recorded as effectful and is still snapshot-undoable on the model side, which takes back the edit and not the write. Naming that is the remaining half.
* **Docs**: new **SPEC §6.2** (normative), the `journal` row in §7.2, [dispatcher](/concepts/dispatcher.md) gains "Pure vs effectful, and the command journal", and [command architecture](/design/command-architecture.md) gains a "Resolved 0.2.8" section that answers its own five-item list rather than being rewritten over.
* **Housekeeping**: new conformance case **`14-journal.vs`** (**14/14**) and `bindings/python/journal_test.py` (13 groups / 33 checks). Full sweep green — 15/15 reduce, 8/8 temper, 8/8 scry, all Python and binding suites, `vc_smoke`. ABI **additive only**. Version **0.2.8**, all five sites agreeing.
